# IWG D365 F&O X++ Code Generation Skill

Picks up from the solution design the **iwg-technical-design** skill produces earlier in
this conversation. This skill does not generate code from a raw requirement unless that
design step has already happened (see Step 0). Once the design is in hand, this skill:

1. Reads the linked work item and its parent hierarchy so everything stays traceable
2. Discovers the client's real naming conventions instead of assuming them
3. Inspects the existing models under `PackagesLocalDirectory` and recommends one
4. **Checks the current git branch and gets the work onto a correctly named feature branch**
5. Identifies or creates a Visual Studio **solution** with one development project
6. Generates the **X++ implementation code** once the user approves the plan
7. With the user's go-ahead, **commits and pushes**, **creates the ADO task**, and
   **raises a Pull Request** linked to that task, all under IWG naming conventions

**Do not create SysTest / test-run classes or a test project.** The team doesn't want unit
test classes generated by this skill. Only the implementation objects are produced. If the
user explicitly asks for tests in a given session, ask them to confirm before adding any.

Hard gates. Nothing is written to disk until all of these are satisfied:

- A technical design exists in this conversation (Step 0)
- The user has confirmed the model and prefix (Step 3)
- Work is on the right feature branch (Step 4)
- The solution/project is identified (Step 5)
- The user has approved the implementation plan (Step 6)

Pushing, creating the ADO task, and raising the PR each happen only after the user says yes
(Steps 9–11).

## IWG Naming Conventions (used in Steps 4, 9, 10, 11)

These come from the team's standards. Use them exactly, because branch names, task titles and
PR titles are how people search for and cross-reference work between Jira (DFO) and Azure
DevOps.

### Identifiers to collect

| Identifier | What it is | Example |
|---|---|---|
| `DFO-<id>` | The DFO ticket (Jira). Required for every piece of work | `DFO-64755` |
| `BS-<id>` | The business/support ticket, when one exists | `BS-15174` |
| `ENHANCE-<id>` | The enhancement ticket. Used **instead of** BS for enhancements | `ENHANCE-23525` |
| Feature name | Short PascalCase name, no spaces, derived from the DFO title | `CustomerPaymentProposal` |
| Description | The DFO ticket's title/summary, in readable form | `Customer payment proposal functionality` |
| `<ADO-Id>` | The ID of the ADO task created in Step 10 | `34534` |

If the DFO ID, the BS/ENHANCE ID, or whether this is an enhancement isn't already clear from
the conversation or the design, **ask the user**. Don't guess an ID. A wrong ID links the
work to someone else's ticket. When the DFO ticket is reachable (e.g. via the Atlassian
tools), read its title to build the feature name and description, and show them to the user
to confirm.

### Branch name

| Case | Pattern | Example |
|---|---|---|
| BS ticket exists | `BS-<id>_DFO-<id>_<FeatureName>` | `BS-15174_DFO-64755_CustomerPaymentProposal` |
| No BS ticket | `DFO-<id>_<FeatureName>` | `DFO-64755_CustomerPaymentProposal` |
| Enhancement | `ENHANCE-<id>_DFO-<id>_<FeatureName>` | `ENHANCE-23525_DFO-34734_CustomerPaymentProposal` |

### ADO task title

| Case | Pattern | Example |
|---|---|---|
| BS ticket exists | `[DFO-<id>][BS-<id>] - <description>` | `[DFO-23849][BS-23687] - Customer payment proposal functionality` |
| No BS ticket | `[DFO-<id>] - <description>` | `[DFO-23849] - Customer payment proposal functionality` |
| Enhancement | `[DFO-<id>][ENHANCE-<id>] - <description>` | `[DFO-2344][ENHANCE-34738] - Customer payment proposal functionality` |

### Pull Request title

`<ADO-Id>: <ADO task title>`. Take the task title exactly as created in Step 10 and put the
new task's ID in front.

| Case | Example |
|---|---|
| BS ticket exists | `34534: [DFO-23849][BS-23687] - Customer payment proposal functionality` |
| No BS ticket | `34534: [DFO-23849] - Customer payment proposal functionality` |
| Enhancement | `34534: [DFO-2344][ENHANCE-34738] - Customer payment proposal functionality` |

Also use the ADO task title as the commit message summary line in Step 9.

## Step 0: Confirm the Technical Design Exists (hard gate)

This skill turns an already-reviewed technical design into code. It does not produce that
design itself. The **iwg-technical-design** skill does that, and it should run first in the
same conversation. Generating X++ straight from a raw work item skips the point where object
names, extension points and edge cases get agreed. Code built that way tends to miss things,
and fixing it afterwards costs more than a short pause here.

- **Design already produced in this conversation**: use it as the authoritative context for
  every step that follows. Don't re-derive requirements from scratch.
- **Not yet run**: stop. Don't read work items, touch git, or generate anything. Tell the user:
  > "This skill builds on the technical design that the 'iwg-technical-design' skill
  > produces. I don't see that it's been run yet in this conversation. Could you run it
  > first (e.g. 'run iwg-technical-design for DFO-12345')? Once the solution design is ready,
  > I'll pick up from there and generate the code."

## Step 1: Get the Work Item and Full Context

Use the design from Step 0 as the primary source of truth. Still walk the work item hierarchy
so the ADO task (Step 10) can be linked correctly and the acceptance criteria and tags are on
hand.

**If the user provides an ADO Work Item ID:**

```
azure-devops:wit_work_item  action=get  id=<ID>  expand=All
```

Extract `System.Title`, `System.Description`, `System.WorkItemType`,
`Microsoft.VSTS.Common.AcceptanceCriteria`, `System.Tags`, `System.Parent`. Walk up
`Task → User Story → Feature → Epic` until there is no parent. Treat any linked FDD as the
authoritative design spec.

**If the requirement is a DFO / BS / ENHANCE ticket**: record those IDs now for the naming
conventions above, and fetch the DFO title if the Atlassian tools are available.

**If nothing was given:** ask: "Please share the DFO ticket (and BS/ENHANCE ticket, if any)
or the ADO work item ID."

---

## Step 2: Discover Naming Conventions for Objects (do NOT assume them)

Never invent a client prefix, model name or object naming pattern. Discover it in this order:

1. **Search Azure DevOps for standards:**
   ```
   azure-devops:search_wiki       query="naming convention" / "coding standard" / "X++ standard"
   azure-devops:search_workitem   query="naming convention" / "coding standard" / "prefix"
   ```
2. **Look at the local codebase** (Step 3) for the prefix and casing already used in the
   client's custom models. Use what's there. Don't introduce a new pattern.
3. **If nothing is found**, ask the user which prefix to use for new objects.

Reuse whatever is confirmed for every artefact in this session, and note it in `CLAUDE.md`
(Step 3).

## Step 3: PackagesLocalDirectory Access, Model and Prefix (hard gate)

Ask the user for the `PackagesLocalDirectory` path unless it is already known from the
conversation or a connected folder (e.g. `K:\AosService\PackagesLocalDirectory`). Don't guess
a path. Writing to the wrong location is costly.

### CLAUDE.md

- **Exists at that path**: read it for the model names, naming convention, repo/branch notes
  and prior related work. Use it as ground truth, but verify anything this task depends on.
- **Doesn't exist**: explore the top-level model folders, then create a `CLAUDE.md` that
  summarizes the naming convention, the custom models, and relevant existing objects.

### Recommend a model

List the top-level folders. Treat anything that isn't Microsoft-owned (`ApplicationSuite`,
`ApplicationPlatform`, `ApplicationFoundation`, `ApplicationCommon`, `Dynamics365*`, etc.) as
a candidate client model. Pick the model that already covers the same functional area or
holds related customizations, and explain why in a sentence or two. This is a
recommendation, not a decision.

### Confirm model and prefix

> "To confirm before I go further: should I use the `<model>` model and the `<prefix>`
> prefix for the new objects?"

Wait for an explicit yes or correction. Record the answer and add it to `CLAUDE.md`.

## Step 4: Check the Git Branch and Create the Feature Branch (hard gate)

Do this **before** creating the solution or any objects. Code written onto `main`, `develop`
or someone else's feature branch is hard to separate out later, and it breaks the
branch-per-ticket traceability the team relies on.

### 4a: Find the repo and current branch

Locate the git repo that contains the target model. This is usually the folder that holds
the model or one of its parents. Then check the state:

```
git -C <model-or-repo-path> rev-parse --show-toplevel
git -C <repo> branch --show-current
git -C <repo> status --short
```

If no local shell is available, use `azure-devops:repo_branch` to list branches and ask the
user which branch their workspace is on. If the model folder isn't in a git repo, ask the
user for the repo path rather than guessing.

### 4b: Decide whether a new branch is needed

Build the expected branch name from the conventions table, using the IDs from Step 1. Ask the
user for any missing IDs, or whether this is an enhancement.

- **Already on a branch that matches this ticket** (same DFO/BS/ENHANCE IDs): say so and
  continue on it.
- **On `main` / `master` / `develop` / a release branch, or on a branch for a different
  ticket**: suggest a new branch:
  > "You're currently on `<current-branch>`. For this feature I suggest creating
  > `<proposed-branch-name>` from `<base-branch>`. Shall I create it and switch to it?"

  The base branch defaults to the branch the team develops from, usually the current one if
  it's `develop`/`main`. Confirm it with the user if unclear.
- **Uncommitted changes** show up in `git status`: point them out before switching, so the
  user can decide whether to commit, stash or carry them over. Never discard them.

### 4c: Create and switch

Once the user agrees:

```
git -C <repo> fetch
git -C <repo> checkout -b <branch-name> <base-branch>
git -C <repo> branch --show-current      # verify you're on the new branch
```

If there's no local shell, create the branch with `azure-devops:repo_create_branch` and ask
the user to check it out in their workspace. Wait for them to confirm before writing files.

Record the branch name in `CLAUDE.md` for this feature.

## Step 5: Get / Create the Visual Studio Solution and Project

A single **development project** is all that's needed. No test project, because no test
classes are generated.

### 5a: Ask first

> "Do you already have a solution/project you'd like me to use? If so, give me the solution
> name and path (and the project name if different). Otherwise I'll look for one or create a
> new one."

- **User provides names/paths**: use exactly what they gave. Verify the `.rnrproj` exists.
  If it doesn't, tell them and ask them to double-check. Don't silently search elsewhere.
- **User wants you to check**: `find <path> -iname "*.sln" -maxdepth 4`, list the results
  and ask which one to use.
- **User wants a new one**: go to 5b.

### 5b: Creating a new solution/project

Don't create `.sln`/`.rnrproj` files inside `PackagesLocalDirectory`. That's where AOT
objects live, and it's often restricted. Put the scaffolding in the repo folder or another
accessible location. Ask the user if it's unclear. Project items reference the AOT files at
their `PackagesLocalDirectory` path.

**Project**: `<accessible-path>\<ProjectName>\<ProjectName>.rnrproj`

```xml
<?xml version="1.0" encoding="utf-8"?>
<Project ToolsVersion="4.0" xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <PropertyGroup>
    <ProjectGuid>{<new-guid>}</ProjectGuid>
    <Name><ProjectName></Name>
    <RootNamespace><ProjectName></RootNamespace>
  </PropertyGroup>
  <ItemGroup>
    <!-- e.g. <Compile Include="<PackagesLocalDirectory>\<Model>\AxClass\<ClassName>.xml" /> -->
  </ItemGroup>
</Project>
```

**Solution**: `<accessible-path>\<SolutionName>.sln`

```
Microsoft Visual Studio Solution File, Format Version 12.00
Project("{<solution-type-guid>}") = "<ProjectName>", "<ProjectName>\<ProjectName>.rnrproj", "{<project-guid>}"
EndProject
Global
	GlobalSection(SolutionConfigurationPlatforms) = preSolution
		Debug|Any CPU = Debug|Any CPU
	EndGlobalSection
EndGlobal
```

Tell the user where the solution/project was created and where the AOT objects will go.

## Step 6: Implementation Plan and Approval (hard gate)

Before writing any object, show the plan and wait for approval:

```
### Implementation Plan: [DFO-id][BS-id / ENHANCE-id] - <description>

**Branch:** <feature branch from Step 4>
**Model:** <confirmed model>
**Prefix / naming convention:** <confirmed>
**Solution / Project:** <solution> / <project>

**Objects to create or extend:**
| Object | AOT Type | New / Extension | Purpose |
|---|---|---|---|

**Key design decisions:**
- e.g. CoC extension on CustVendPaymProposal..., new table <Prefix>...
```

Ask: *"Does this plan look right? Once you're happy with it, I'll create the objects."*
If the user asks for changes, revise the plan and ask again. Only create objects after a
clear yes.

## Step 7: Generate X++ Code

Follow the general X++ patterns in `references/xpp-conventions.md` if that file is present.
Always substitute the confirmed prefix for any example prefix shown in it.

| Requirement signals | Artefact |
|---|---|
| New entity / data storage | New Table (`AxTable`) |
| Add field to existing table | Table Extension (`AxTableExtension`) |
| Business logic / service | Class (`AxClass`) |
| Scheduled automation | `SysOperation` controller/service/contract |
| Modify existing form | Form Extension (`AxFormExtension`) |
| New screen | New Form (`AxForm`) |
| Reporting | SSRS / ER (note only, don't generate) |
| Data import/export | Data Entity (`AxDataEntityView`) |
| Number sequence | Number sequence extension in model descriptor |

### Code quality rules

- No overlayering. Use extensions and Chain of Command, and always call `next`.
- Always add `[ExtensionOf(tableStr(...))]` / `[ExtensionOf(classStr(...))]`.
- Table extensions are named `[BaseTableName].Extension` in the client model.
- Use `ttsbegin`/`ttscommit` around writes. Never use `select *`, only the fields you need.
- Add XML doc comments on public methods.
- Prefer `SysOperation` over `RunBase`, and use `RecordInsertList` for bulk inserts.
- Respect `SysDatabaseLogEnabled` for auditable tables.
- **Don't generate SysTest classes, test-run classes or a test project.**

### Write and register

Write each file under `<PackagesLocalDirectory>\<Model>\<AxType>\<Name>.xml`, and straight
away add its item entry to the `.rnrproj` from Step 5. If a needed model folder doesn't
exist, ask before creating it.

## Step 8: Summary and Review

```
### Objects Created on branch <branch>

| File | Path | AOT Type | Project | Status |
|------|------|----------|---------|--------|

**Solution/Project:** <location>
**AOT objects:** <PackagesLocalDirectory path>
```

Tell the user the objects are in the project and ready to build in Visual Studio. Then ask:

> "Please build and review the changes. When you're happy, shall I push them to
> `<branch>` and create the ADO task and Pull Request?"

If the user wants changes, make them and ask again. Don't push until they say yes.

## Step 9: Commit and Push (only after the user says yes)

1. Show `git status --short` so the user can see exactly which files go into the commit.
   Stage only this feature's files: the model objects and the project/solution files. Leave
   out unrelated changes in the workspace, and mention them to the user.
2. Commit, using the ADO task title convention as the summary line:
   ```
   git -C <repo> add <files>
   git -C <repo> commit -m "[DFO-<id>][BS-<id>] - <description>"
   git -C <repo> push -u origin <branch>
   ```
3. If the push fails (auth, rejected, no remote), report the error to the user and stop.
   Don't force-push.

## Step 10: Create the ADO Task

Create the task after the push, so the PR in Step 11 can reference it.

```
azure-devops:wit_work_item_write  action=create
  project: <project>
  type: Task
  fields:
    System.Title: "[DFO-<id>][BS-<id>] - <description>"     (see naming table for no-BS / ENHANCE)
    System.Description: <content below>
```

If the user gave a parent ADO work item (User Story/Feature) in Step 1, link the task to it
as a child with `azure-devops:wit_work_item_link_write`.

Description content:

```
## [DFO-id][BS-id] - <description>

### Summary
<1–2 sentences on what was implemented>

### Branch / Solution
- Branch: <branch>
- Solution / Project: <solution> / <project>
- Model: <model>

### Objects Created
| Object | Type | Purpose |
|---|---|---|

### Key Logic (pseudocode)
<plain-language logic, enough for a reviewer to follow without reading the code>

### Naming Convention Used
<prefix/pattern>
```

Record the new task ID. Step 11 needs it.

## Step 11: Create the Pull Request and Link the Task

The **azure-devops-pr-creator** skill can be used for the mechanics, such as choosing
reviewers. The title and work item link below still apply.

```
azure-devops:repo_pull_request_write  action=create
  repository: <repo>
  sourceRefName: refs/heads/<branch>
  targetRefName: refs/heads/<base-branch from Step 4>
  title: "<ADO-Id>: [DFO-<id>][BS-<id>] - <description>"
  description: <summary + object list from Step 10>
  workItems: <ADO-Id>
```

Ask the user who should review, if they haven't said. After the PR is created, check that
the ADO task shows as linked on the PR. If the create call couldn't attach it, add the link
separately (an artifact link from the task to the PR) before you report back.

Confirm to the user:

> "Pushed `<branch>`, created ADO task #<ADO-Id> `[DFO-...][...] - ...`, and raised PR
> #<PR-Id> `<ADO-Id>: [DFO-...][...] - ...` into `<base-branch>`, with the task linked."

## Edge Cases

| Situation | How to handle |
|---|---|
| iwg-technical-design not run yet | Stop at Step 0 and ask the user to run it first |
| Model/prefix not confirmed | Stop at Step 3. Don't assume a default |
| DFO ID unknown | Ask. Every branch, task and PR name needs it |
| Unsure whether BS or ENHANCE applies | Ask. Use BS for business/support tickets and ENHANCE for enhancements; never both |
| No BS and not an enhancement | Branch `DFO-<id>_<Feature>`, task `[DFO-<id>] - <desc>` |
| Already on a matching feature branch | Continue on it. No new branch needed |
| On main/develop or another ticket's branch | Suggest the correctly named branch and create/switch only after the user agrees |
| Uncommitted changes before switching branch | Show them and let the user decide. Never discard |
| Model folder not in a git repo | Ask for the repo path |
| User declines a new branch | Warn once that the objects will land on `<current-branch>`, then follow their choice |
| User asks for unit tests | This skill doesn't generate test classes by default. Confirm explicitly before adding any |
| Push or PR creation fails | Report the exact error. Don't force-push or retry blindly |
| Requirement is a standard fit (no code) | Say so, and don't generate code, branch or PR |
| Work item is vague / no acceptance criteria | Ask one focused question before planning |
| Parent Epic conflicts with the Task | Prefer the Task-level detail and note the conflict |
| CLAUDE.md exists but looks stale | Use it as a starting point, but verify anything this task depends on |
| Target model folder doesn't exist | Confirm with the user before creating a new model |

## Skill Feedback Loop: Teaching the FitGap Skill

### When to trigger

Write a correction to the Knowledge Base when, during code generation:

| Situation | Example |
|---|---|
| FitGap said Fit but X++ is actually needed | "Standard periodic billing" → needs custom contract table |
| FitGap said Gap but a standard D365 pattern exists | "Custom approval" → standard workflow engine |
| A blocked approach was abandoned for a better one | DMF entity instead of custom CSV upload form |
| Standard D365 behaviour differs from what fitgap assumed | Payment terms override needs CoC, not config |

### How to write back

1. Find the KB item (never create it; fitgap owns it):
   `azure-devops:search_workitem query="[CLAUDE] FitGap Knowledge Base" project="FinOpswithClaude"`.
   If it isn't found, tell the user to run a fitgap analysis first.
2. Read its `System.Description`. Find the last `KB-[NNN]` between `<!-- ENTRIES START -->`
   and `<!-- ENTRIES END -->`, then increment it (start at KB-001 if there are none).
3. Build the entry:
   ```
   ## KB-[NNN] — [Short Requirement Pattern]
   - **Original Verdict:** ...
   - **Corrected Verdict:** ...
   - **What Was Wrong:** ...
   - **Actual D365 F&O Behaviour:** ...
   - **Correct Solution:** ...
   - **Work Item Reference:** #[ID]
   - **Recorded By:** iwg-fo-codegen
   - **Date:** [YYYY-MM-DD]
   ```
4. Append it before `<!-- ENTRIES END -->` and update the item with
   `azure-devops:wit_work_item_write action=update project="FinOpswithClaude"`.
5. Tell the user: "I've recorded correction KB-[NNN] to the FitGap Knowledge Base."

Rules: always append and never overwrite; read before writing; never create the KB item;
always use the project `"FinOpswithClaude"`.
